# Behavior contracts, discovery, and implementation replacement

Date: November 3, 2026. This refines the [consolidated roadmap](ai-era-consolidated-roadmap.md). The [workspace](../demo/pr-workbench/README.md) demonstrates the product model; general legacy analysis remains future work.

## Product model

Undertow connects standing system contracts, intended changes, independent evaluations, and their provenance. A PR is one comparison subject. A service extraction, regenerated module, or replacement implementation is another. A contract need not originate in the latest change.

Preserve an executable description of required behavior across implementations, retain why a change was made, and expose gaps. Passing new-feature tests alone cannot establish that existing obligations survived.

| Artifact | Meaning | Authority |
|---|---|---|
| Standing contracts | Existing obligations, such as aggregate refund limits and retry semantics. | Owner-approved, pinned policy and verifier inventory. |
| Change intention | New behavior, boundary, rationale, intentional differences, assumptions. | Proposal until reviewed; free text is not an executable oracle. |
| Discovered candidates | Observations/hypotheses from tests, code, schemas, interfaces, authorized traces. | Unapproved, source-linked candidates. |
| Candidate verifier | Characterization/property/counterexample tests proposed to close a gap. | Execution does not approve expected behavior. |
| Evaluation evidence | Exact check executions against source/artifact subjects and oracle versions. | Both provenance and adequacy matter. |
| Operational evidence | Relevant traffic, side effects, drift, containment, reconciliation. | Environment-specific authenticated observations. |

The existing verifier evaluates every declared contract on every subject; `scope` does not skip requirements based on touched files. An observed legacy bug is not automatically a requirement. Intentional behavior changes need reviewed contract versions. Agents and anonymous UI edits cannot silently promote them.

## Authoring and workspace

Use versioned YAML/JSON for contract identity, ownership, expectations, assumptions, scope, and exact test bindings. Both representations use the existing version 1 manifest. The expectation is human-readable; the approved verifier makes a particular check executable. A sentence is not automatically a correct predicate.

Use Markdown/free text for change intention and architectural rationale. The browser edits JSON with native parsing and no frontend dependencies. The existing YAML-capable CLI reads it with `--manifest contracts.json`; this is not a second contract language. Browser validation is structural preflight; the CLI performs full schema/source checks.

The UI is an engineering workbench: boundary context, standing/proposed files, source/verifier inspection, replay input, and baseline/candidate evidence. Draft edits do not retroactively rebind recorded executions. Removing a contract from a draft cannot hide a standing-policy failure. There is no consumer wizard or aggregate safety score.

## Refund extraction example

The [Java fixture](../demo/refund-extraction/README.md) compares three domain implementations:

| Subject | Standing behavior | Proposed partial refunds |
|---|---|---|
| Legacy | Full refunds only; aggregate cap and retries hold. | Not implemented; proposed assertions fail. |
| Broken extraction | Checks each request against the original capture, ignoring earlier refunds. An existing second-full-refund check fails. | A 2,500 refund succeeds, yet 8,000 plus 3,000 can exceed a 10,000 capture. |
| Corrected extraction | Uses the remaining captured balance and preserves operation keys. | Partial refunds share the same aggregate budget. |

Standing `REFUND-CAP` and `REFUND-RETRY` contracts are separate from proposed `PARTIAL-REFUND`. The same existing tests execute against all implementations regardless of implementation size. Six checks per variant and two temporary-probe executions are recorded.

The temporary probe is generated by a reviewed fixture template, materialized in ignored output copies, and compiled/executed against broken/corrected sources. It tests 8,000 plus 3,000 against 10,000. It remains a candidate and is not added to standing policy. Errors/missing reports cannot count as detection. This is not live model generation or a generic arbitrary-code executor.

The model is sequential, in memory, and single-currency. It does not establish real provider totals, concurrent reservations, persistent idempotency, authentication, data migration, distributed transactions, FX, or deployment behavior. It models domain extraction, not an actual deployed service migration.

## Monolith discovery and replacement

1. **Inventory a boundary.** Map entry points, data ownership, transactions, external effects, tests, SQL constraints, interfaces, ADRs/incidents, and authorized sanitized traces. Preserve revisions and coverage gaps.
2. **Observe.** Extract descriptions, assertions, fixture conditions, transitions, errors, interface shapes, and side effects. Distinguish source facts from semantic hypotheses. One oversized-refund assertion cannot establish every cumulative/concurrent case.
3. **Propose.** Group observations into candidate invariants with supporting sources, tested conditions, assumptions, owner, counterexamples, missing evidence, and possible legacy-defect interpretations. Do not invent confidence percentages.
4. **Curate.** Owners identify business obligations, implementation details, intended changes, and bugs. Mock-heavy unit tests inform discovery without necessarily becoming permanent cross-implementation oracles.
5. **Strengthen evaluation.** Propose characterization/property/counterexample tests for specific gaps. Check sensitivity with relevant valid mutations and independent baseline/candidate runs. Execute generated code in bounded disposable CI outside the model worker, with credential/publisher separation. Reuse the existing [external regression and isolation path](assurance.md).
6. **Replace one component.** Put behavioral checks behind adapters/stable interfaces to evaluate both implementations. Preserve API/event/data obligations; record intended differences. Approved remapping may replace old class/test bindings without preserving obsolete internals.
7. **Observe and cut over.** Use authorized shadow/replay/canary evidence with meaningful traffic. Never duplicate real refund effects by shadow-writing to another provider path. Bind the deployed artifact to evidence. Define containment and reconciliation; code rollback cannot undo a settled refund.

Discovery records should retain expectation, source paths/lines/revisions, check identities and statuses, observation scope, uncertainty, missing counterexamples, owner, and approval state. Accepted candidates become contracts through ownership review. Generated tests cannot approve themselves or weaken the required suite.

The prototype inventories four existing `@DisplayName` declarations with exact sources/hashes and copies a selected candidate into an unapproved manifest draft. It does not infer arbitrary Java semantics, cluster enterprise monoliths, mine unrestricted traces, or call a model. General discovery is a next increment. Models may help synthesize proposals when access, consent, and budgets are configured, while execution and approval remain independent.

## Next acceptance target

Choose one real Java/Maven boundary and owner. Inventory current checks, approve two or three durable obligations, identify one uncovered business case, and add an independently reviewed oracle. Compare a bounded replacement with the legacy implementation in shadow mode. Measure candidate usefulness, owner corrections, missing evidence, false positives, sensitivity, and failure-understanding time. A curated fixture and illustrative owner do not substitute for that pilot.
